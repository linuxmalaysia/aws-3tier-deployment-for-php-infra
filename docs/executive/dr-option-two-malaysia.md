# DR Option Two: Malaysia Region & Cross-Account Replication Strategy

This document establishes the detailed architecture, copying procedures, discovery commands, and pricing calculator configurations for **Disaster Recovery (DR) Option Two: Same-Region (Malaysia, `ap-southeast-5`) with a Separate AWS Account**.

By leveraging account-level isolation within the same sovereign borders, this design protects the primary 3-tier PHP (CodeIgniter & Fusio) workload against administrative accidents, accidental resource deletion, ransomware, and credential compromise. It achieves this while complying fully with the Malaysian Personal Data Protection Act (PDPA) 2010/2024 by maintaining 100% of transaction data, logs, and metadata within the `ap-southeast-5` geographical zone.

---

## 1. DR Option Two Architecture & Sovereignty

Unlike Option One (Cross-Region DR to Singapore), which introduces cross-border compliance overhead under PDPA Section 129, Option Two isolates the disaster recovery environment within the **AWS Asia Pacific (Malaysia) Region (`ap-southeast-5`)** under an entirely **separate AWS Account**.

### Rationale for Same-Region Account Segregation:
1. **Administrative Boundary Protection:** The primary risk factor in enterprise cloud operations is often not a complete AWS regional failure, but rather control-plane compromise, administrative errors, API key leakage, or ransomware. Separating accounts creates a strict security wall.
2. **Sovereign Data Residency:** Since all resources remain inside `ap-southeast-5`, there are no cross-border data transfer issues. No Transfer Impact Assessments (TIAs) or Standard Contractual Clauses (SCCs) are needed for cross-border transfers since no data leaves the country.
3. **Low Latency & High Speed Sync:** Because replication occurs within the same AWS region, cross-account replication is extremely fast, near-zero latency, and avoids cross-region data transfer charges.

## 2. Copying the Production Stack: Step-by-Step Mechanisms

To replicate the production stack from the primary account to the standby account, we implement standardized, service-level copying mechanisms.

```text
┌────────────────────────────────────────────────────────────────────────┐
│               Cross-Account Same-Region Copying Flow                   │
│                                                                        │
│  [ Primary AWS Account ]                   [ Standby DR AWS Account ]  │
│                                                                        │
│  - OpenTofu Code (GitHub) ───────────────► Tofu Apply (Target Account) │
│  - Baked Golden AMI (ASIMP) ─────────────► Share AMI Launch Perms      │
│  - S3 Production Bucket ─────────────────► S3 Cross-Account CRR        │
│  - RDS MariaDB Snapshot ─────────────────► Share Snapshot & Restore    │
│  - EFS Config Assets ────────────────────► AWS Backup Cross-Account    │
└────────────────────────────────────────────────────────────────────────┘
```

### A. Infrastructure as Code (IaC) Replication
We do not configure resources manually in the standby account. We use the **same OpenTofu code** in the standby account.
1. Create a separate OpenTofu workspace or backend configuration (S3 bucket and DynamoDB lock table) inside the Standby Account.
2. Parameterize the `variables.tf` files to specify the target AWS Account ID, subnets, and slightly altered CIDR block ranges if VPC Peering is planned (to avoid overlapping CIDR blocks, e.g., Primary VPC = `10.0.0.0/16`, Standby VPC = `10.1.0.0/16`).
3. Execute `tofu init` and `tofu apply` in the Standby Account to provision the exact same 3-tier structure (ALB, ASG, RDS, Valkey, SGs, and WAFv2).

### B. Machine Image Copying (Golden AMIs)
We use the same baked, hardened Debian/Ubuntu and RHEL golden AMIs generated by Packer and hardened with **ASIMP (Ansible System Integrity Management Platform)**:
1. Identify the production Golden AMI ID in the primary account.
2. Modify the AMI launch permissions to share it with the target Standby Account:
   ```bash
   aws ec2 modify-image-attribute \
     --image-id ami-0123456789abcdef0 \
     --launch-permission "Add=[{UserId=STANDBY_ACCOUNT_ID}]"
   ```
3. In the Standby Account, reference this shared AMI in the OpenTofu variable files as the base for the Auto Scaling Group (ASG) Launch Template.

### C. Database Replication (MariaDB RDS)
Since native RDS Multi-Account Read Replicas are not directly supported out-of-the-box as a simple click, we use one of three cross-account strategies:
1. **AWS Backup Cross-Account Copy:**
   - Configure a backup vault in the primary account and a backup vault in the standby account.
   - Share the primary vault's KMS key with the standby account.
   - Set up an AWS Backup copy job to copy database snapshots across accounts.
2. **RDS Snapshot Sharing and Restore (RTO: 1-2 Hours, RPO: Daily):**
   - Share the latest daily automated RDS MariaDB snapshot with the Standby Account.
   - Copy the shared snapshot to the Standby Account using the local KMS key.
   - Restore the DB instance from the snapshot.
3. **GTID-based Binlog replication over VPC Peering (RTO: < 15 Mins, RPO: Seconds):**
   - Establish a secure VPC Peering link between the primary and standby VPCs.
   - Configure a dedicated replication user with `REPLICATION CLIENT` and `REPLICATION SLAVE` privileges on the Primary MariaDB.
   - Set up GTID-based binlog replication using the external master RDS APIs:
     ```sql
     CALL mysql.rds_set_external_master_gtid('primary-db-private-ip', 3306, 'repl_user', 'password', 'gtid_mode', 1);
     CALL mysql.rds_start_replication;
     ```

### D. Object Storage Replication (Amazon S3)
To ensure user uploads are continuously replicated to the DR account:
1. Enable **S3 Versioning** on both primary and standby buckets.
2. Define a **S3 Replication Rule** (Cross-Account Bucket Replication - CRR).
3. Grant the primary account's replication IAM role permission to write to the standby account's bucket by updating the standby bucket's Bucket Policy.

### E. Shared Configurations & Code (Amazon EFS)
Replicate custom configurations or shared application uploads using **AWS Backup Cross-Account Copy**:
1. Run a daily or hourly backup of the primary EFS file system.
2. Automatically copy the recovery point to the Standby Account's backup vault and mount it onto the standby EFS.

## 3. AWS CLI Infrastructure Discovery Commands

To query configuration details from the active production setup so you can share exact specifications with stakeholders and model them in the AWS Pricing Calculator, execute the following CLI commands.

### A. Network & Security Discovery
Identify VPCs, subnets, route tables, and security groups:
```bash
# List all VPCs in ap-southeast-5
aws ec2 describe-vpcs --region ap-southeast-5

# List all subnets and their CIDR ranges
aws ec2 describe-subnets --region ap-southeast-5 \
  --query "Subnets[*].[SubnetId,CidrBlock,AvailabilityZone,MapPublicIpOnLaunch]" --output table

# Discover active Security Groups and Ingress Rules
aws ec2 describe-security-groups --region ap-southeast-5 \
  --query "SecurityGroups[*].[GroupId,GroupName,Description]" --output table
```

### B. Compute & ASG Discovery
Identify instance sizes, launch configurations, and AMI IDs:
```bash
# Discover Auto Scaling Groups and capacity parameters
aws autoscaling describe-auto-scaling-groups --region ap-southeast-5 \
  --query "AutoScalingGroups[*].[AutoScalingGroupName,MinSize,MaxSize,DesiredCapacity,LaunchTemplate.LaunchTemplateName]" --output table

# List active EC2 instances
aws ec2 describe-instances --region ap-southeast-5 \
  --filters "Name=instance-state-name,Values=running" \
  --query "Reservations[*].Instances[*].[InstanceId,InstanceType,Placement.AvailabilityZone,ImageId]" --output table
```

### C. Load Balancer & WAF Discovery
Identify ALB configuration and associated Web ACLs:
```bash
# Discover active Application Load Balancers
aws elbv2 describe-load-balancers --region ap-southeast-5 \
  --query "LoadBalancers[*].[LoadBalancerArn,DNSName,Scheme,Type]" --output table

# List regional WAF Web ACLs
aws wafv2 list-web-acls --scope REGIONAL --region ap-southeast-5
```

### D. Database & Cache Discovery
Identify RDS MariaDB and ElastiCache Valkey specifications:
```bash
# Discover RDS instances, engine versions, and storage configurations
aws rds describe-db-instances --region ap-southeast-5 \
  --query "DBInstances[*].[DBInstanceIdentifier,Engine,EngineVersion,DBInstanceClass,AllocatedStorage,MultiAZ]" --output table

# Discover ElastiCache clusters
aws elasticache describe-cache-clusters --region ap-southeast-5 \
  --query "CacheClusters[*].[CacheClusterId,Engine,CacheNodeType,NumCacheNodes]" --output table
```

## 4. Disaster Recovery Strategies under Account Separation

Option Two supports three core deployment topologies under account separation, allowing organisations to trade off cost versus RTO/RPO targets.

### A. Pilot Light (Sized-to-Zero Compute)
* **Database Strategy:** Active asynchronous database sync (via external replication or frequent shared backup restores).
* **Compute Strategy:** Standby Auto Scaling Group is configured with `desired_capacity = 0`.
* **Failover Protocol:**
  - Upon primary account outage or compromise, scale the standby ASG to `desired_capacity = 2`.
  - Point Route 53 DNS records to the standby Application Load Balancer.
  - **RTO:** 15–30 minutes (ASG instance boot and warm-up time).
  - **RPO:** < 5 seconds (with active binlog replication) or 24 hours (with daily backup share).

### B. Warm Standby (Scaled-down Compute)
* **Database Strategy:** Active asynchronous database sync (standby RDS instance size matches primary or is one size smaller).
* **Compute Strategy:** Standby Auto Scaling Group is configured with `desired_capacity = 1`. One active t4g.micro instance is running at all times.
* **Failover Protocol:**
  - Standard user traffic immediately hits the 1 healthy standby instance.
  - ASG scaling policies trigger automatically to scale the cluster to `desired_capacity = 2` or higher to match production traffic.
  - **RTO:** < 5 minutes (immediate redirection, followed by auto-scaling).
  - **RPO:** < 5 seconds.

### C. Active/Active (Read-Local, Write-Global)
* **Database Strategy:** Since MariaDB RDS is single-writer, all database write operations (INSERT, UPDATE, DELETE) are forwarded via a secure transit link to the primary account's MariaDB instance. All database reads are served locally from a cross-account replica in the standby account.
* **Compute Strategy:** Both accounts run full-capacity active ASGs, sharing user load.
* **Failover Protocol:**
  - If the primary account's database goes offline, promote the standby account's database to master and update application configurations to route write traffic locally.
  - **RTO:** Near-Zero for reads, < 2 minutes for full write promotion.
  - **RPO:** < 2 seconds.

## 6. Implementation Summary

To implement Option Two successfully, the operations team must:
1. Set up a **new AWS account** and configure AWS Organizations to link the accounts under a consolidated billing family.
2. Establish a **VPC Peering connection** or use AWS Transit Gateway between the primary and standby VPCs to allow private replication traffic (such as database sync, if active).
3. Apply the existing **OpenTofu code** to provision identical structures, using separate variables for CIDRs.
4. Share the hardened **Packer/ASIMP Golden AMIs** across the account boundary.
5. Setup **S3 Bucket Replication** and **AWS Backup copy policies** to handle file and database state syncing.
